# 工具配置原理

> **本文档说明**：anyaitools 如何配置 Claude Code、Codex、Gemini CLI、OpenCode 四个工具，以及各工具的配置文件如何起作用。

---

## 一、配置架构概览

### 1. 三层架构

```
┌─────────────────────────────────────────────────────────────┐
│                     用户操作层 (CLI/Desktop)                  │
│  anyaitools add/edit/switch/remove                                │
└─────────────────────────────────────────────────────────────┘
                            ↓
┌─────────────────────────────────────────────────────────────┐
│                   管理层 (ToolManager)                        │
│  - 统一 Provider 数据模型                                     │
│  - 统一 CRUD 操作                                            │
│  - 配置文件：~/.anyaitools/{tool}.json                            │
└─────────────────────────────────────────────────────────────┘
                            ↓
┌─────────────────────────────────────────────────────────────┐
│                    写入层 (Writers)                           │
│  - writeClaudeConfig()  → ~/.claude/settings.json           │
│  - writeCodexConfig()   → ~/.codex/config.toml + auth.json  │
│  - writeGeminiConfig()  → ~/.gemini/settings.json + .env    │
│  - writeOpenCodeConfig() → ~/.config/opencode/opencode.json │
└─────────────────────────────────────────────────────────────┘
                            ↓
┌─────────────────────────────────────────────────────────────┐
│                  工具读取配置并生效                            │
│  Claude Code / Codex / Gemini CLI / OpenCode                │
└─────────────────────────────────────────────────────────────┘
```

### 2. 核心数据模型

**Provider（服务商）**：

```typescript
interface Provider {
  id: string // 唯一标识，格式：{tool}-{timestamp}-{random}
  name: string // 显示名称，如 "OKMCode"
  desc?: string // 描述
  baseUrl: string // API 基础 URL
  apiKey: string // API 密钥
  model?: string // 模型名称或 JSON 元数据
  createdAt: number // 创建时间戳
  lastModified: number // 最后修改时间戳
  lastUsedAt?: number // 最后使用时间戳
}
```

**ToolConfig（工具配置）**：

```typescript
interface ToolConfig {
  providers: Provider[] // Provider 列表
  presets: PresetTemplate[] // 用户自定义预设
  currentProviderId?: string // 当前激活的 Provider ID
}
```

## 二、Claude Code 配置原理

### 1. 配置文件路径

```
~/.claude/settings.json
```

### 2. 配置文件结构

```json
{
  "model": "sonnet",
  "env": {
    "ANTHROPIC_AUTH_TOKEN": "sk-ant-xxx",
    "ANTHROPIC_BASE_URL": "https://okmcode.com/api",
    "CLAUDE_CODE_DISABLE_NONESSENTIAL_TRAFFIC": 1,
    "CLAUDE_CODE_MAX_OUTPUT_TOKENS": 32000
  },
  "permissions": {
    "allow": [],
    "deny": []
  },
  "alwaysThinkingEnabled": true
}
```

### 3. 关键字段说明

| 字段                                           | 作用                       | anyaitools 管理                               |
| ---------------------------------------------- | -------------------------- | --------------------------------------------- |
| `env.ANTHROPIC_AUTH_TOKEN`                     | API 密钥                   | ✅ 强制覆盖                                   |
| `env.ANTHROPIC_BASE_URL`                       | API 基础 URL               | ✅ 强制覆盖                                   |
| `env.CLAUDE_CODE_DISABLE_NONESSENTIAL_TRAFFIC` | 禁用非必要流量             | ✅ 默认值 1                                   |
| `env.CLAUDE_CODE_MAX_OUTPUT_TOKENS`            | 最大输出 Token 数          | ✅ 默认值 32000                               |
| `permissions`                                  | 权限配置                   | ❌ 保留用户配置                               |
| `model`                                        | 模型选择                   | ✅ 模板默认 `sonnet`（动态解析到最新 Sonnet） |
| `alwaysThinkingEnabled`                        | 默认启用 extended thinking | ✅ 默认 `true`                                |

### 4. 写入策略（零破坏性）

**代码位置**：`packages/core/src/writers/claude.ts`

**流程**：

```typescript
// 1. 读取用户现有配置
let userConfig = {}
if (fileExists(configPath)) {
  userConfig = JSON.parse(fs.readFileSync(configPath, 'utf-8'))
}

// 2. 替换模板变量，生成默认配置
const defaultConfig = replaceVariables(CLAUDE_CONFIG_TEMPLATE, {
  apiKey: provider.apiKey,
  baseUrl: provider.baseUrl,
})

// 3. 深度合并：默认配置为基础，用户配置覆盖
const mergedConfig = deepMerge(defaultConfig, userConfig)

// 4. 强制更新认证字段为最新值
mergedConfig.env.ANTHROPIC_AUTH_TOKEN = provider.apiKey
mergedConfig.env.ANTHROPIC_BASE_URL = provider.baseUrl

// 5. 写入配置文件
fs.writeFileSync(configPath, JSON.stringify(mergedConfig, null, 2))
```

**保证**：

- ✅ 用户的 `permissions` 配置不会丢失
- ✅ 用户的其他 `env` 变量不会丢失
- ✅ 常规 merge 时保留用户已有的 `model`；新文件和 overwrite 默认使用 `sonnet`
- ✅ 认证字段始终是最新的

### 5. Claude Code 如何读取配置

**启动时**：

1. 读取 `~/.claude/settings.json`
2. 从 `env.ANTHROPIC_AUTH_TOKEN` 获取 API Key
3. 从 `env.ANTHROPIC_BASE_URL` 获取 Base URL
4. 读取 `model = "sonnet"` 作为默认模型别名
5. 使用这些配置连接 API 服务

**环境变量优先级**：

```
系统环境变量 > settings.json 中的 env > 默认值
```

## 三、Codex 配置原理

### 1. 配置文件路径

```
~/.codex/config.toml    # 主配置
~/.codex/auth.json      # 认证信息
```

### 2. config.toml 结构

只列关键字段（完整模板见 `packages/core/templates/codex/config.toml`）：

```toml
model_provider = "okmcode"
model = "gpt-5.5"

[model_providers.okmcode]
base_url = "https://okmcode.com"
```

### 3. auth.json 结构

```json
{
  "OPENAI_API_KEY": "sk-ant-xxx"
}
```

### 4. 关键字段说明

| 字段                                                         | 作用                 | anyaitools 管理                                                              |
| ------------------------------------------------------------ | -------------------- | ---------------------------------------------------------------------------- |
| `model_provider`                                             | 当前使用的服务商 key | ✅ 默认更新；保护开关开启且已有非空值时保持原名称                            |
| `model`                                                      | 当前使用的模型       | ✅ `provider.model` 优先；常规 merge 否则保留已有值，新文件使用模板值        |
| `model_providers[name]`                                      | 服务商配置           | ✅ 更新当前 provider 的托管字段；常规 merge 保留其他 provider 和合法传输扩展 |
| 其他字段（如 `approval_policy` / `features` / `history` 等） | Codex 运行参数       | ✅ 常规 merge 保留；明确废弃的根键和 feature 会自动清理                      |
| `auth.json.OPENAI_API_KEY`                                   | API 密钥             | ✅ 强制更新；常规 merge 保留 auth.json 的其他字段                            |

Codex 0.134.0 起不再从 `config.toml` 读取顶层 `profile` 和内联 `profiles.*`。anyaitools 不再生成这两个旧字段，并会在更新 `config.toml` 时将其清理；如需 profile，请改用 `~/.codex/<name>.config.toml` 与 `codex --profile <name>`。

### 5. 写入策略（常规 merge + 快捷 overwrite）

**代码位置**：`packages/core/src/writers/codex.ts`

**流程**：

```typescript
// 1. 常规切换：解析现有配置；解析失败直接中止，不覆盖原文件
const existingConfig = loadExistingCodexConfig(configPath)
const templateConfig = loadCodexTemplateConfig()
const nextConfig = deepMerge(templateConfig, existingConfig)

// 2. 清理明确废弃的键，并更新当前 provider
removeDeprecatedKeys(nextConfig)
const providerKey =
  preserveProviderName && existingConfig.model_provider
    ? existingConfig.model_provider
    : resolveCodexProviderKey(provider)
nextConfig.model_provider = providerKey
nextConfig.model = provider.model || nextConfig.model || 'gpt-5.5'
nextConfig.model_providers = {
  ...otherProviders,
  [providerKey]: {
    ...safeExistingProviderExtensions,
    name: providerKey,
    base_url: provider.baseUrl,
    wire_api: 'responses',
    requires_openai_auth: true,
  },
}

// 3. 写入 config.toml；auth.json 只强制更新 OPENAI_API_KEY
fs.writeFileSync(configPath, stringifyToml(nextConfig))
writeJSON(authPath, { ...existingAuth, OPENAI_API_KEY: provider.apiKey })
```

**保证**：

- ✅ `aat cx use`、Desktop 切换和编辑当前 provider 默认使用 merge
- ✅ Desktop 的“保护 model_provider”开关默认关闭；开启后普通 merge 保留已有顶层名称，并更新同名 provider 块
- ✅ 保留其他 provider、普通根字段、有效 feature 及当前 provider 的 headers/query/retry 等扩展
- ✅ TOML 或 auth.json 无法解析时 fail closed，原文件不会被静默重建
- ✅ `aat okm`、aicoding、standalone 和安装脚本等快捷入口使用 overwrite
- ✅ overwrite 仅保留模板和当前 provider；需要恢复时使用快捷入口创建的备份
- ✅ overwrite 不应用名称保护开关，继续按模板和目标 provider 重建

**注意**：

- ⚠️ TOML 解析器会丢失注释（已知限制）
- ⚠️ 常规 switch 不生成 `.bak`；高风险快捷覆盖入口由调用方负责写前备份

### 6. Codex 如何读取配置

**启动时**：

1. 读取 `~/.codex/config.toml`
2. 从 `model_provider` 获取当前服务商名称
3. 从 `model_providers[name]` 获取服务商配置
4. 读取 `~/.codex/auth.json` 获取 API Key
5. 使用这些配置连接 API 服务

**配置优先级**：

```
命令行参数 > config.toml > 默认值
```

## 四、Gemini CLI 配置原理

### 1. 配置文件路径

```
~/.gemini/settings.json    # 主配置
~/.gemini/.env             # 环境变量
```

### 2. settings.json 结构

只列关键字段（完整模板见 `packages/core/templates/gemini/settings.json`）：

```json
{
  "ide": { "enabled": true },
  "security": { "auth": { "selectedType": "gemini-api-key" } }
}
```

### 3. .env 结构

只列关键字段（完整模板见 `packages/core/templates/gemini/.env`）：

```bash
GOOGLE_GEMINI_BASE_URL=https://okmcode.com
GEMINI_API_KEY=sk-ant-xxx
GEMINI_MODEL=gemini-3.5-flash
```

### 4. 关键字段说明

| 字段                         | 作用          | anyaitools 管理                                       |
| ---------------------------- | ------------- | ----------------------------------------------------- |
| `ide.enabled`                | 启用 IDE 集成 | ✅ 确保为 true                                        |
| `security.auth.selectedType` | 认证方式      | ✅ 默认 "gemini-api-key"                              |
| `GEMINI_API_KEY`             | API 密钥      | ✅ 设置为 provider.apiKey                             |
| `GOOGLE_GEMINI_BASE_URL`     | API 基础 URL  | ✅ 设置为 provider.baseUrl                            |
| `GEMINI_MODEL`               | 模型名称      | ✅ 模板默认 `gemini-3.5-flash`，provider.model 可覆盖 |

### 5. 写入策略（模板 + 零破坏性）

**代码位置**：`packages/core/src/writers/gemini.ts`

**流程**：

```typescript
// 1. 读取模板并与现有 settings.json 深度合并
const templateSettings = loadGeminiSettingsTemplate()
const userSettings = fileExists(settingsPath) ? JSON.parse(fs.readFileSync(settingsPath)) : {}
const settings = deepMerge(templateSettings, userSettings)

// 确保启用 IDE 集成
settings.ide = settings.ide || {}
if (settings.ide.enabled === undefined) {
  settings.ide.enabled = true
}

// 配置认证方式（默认值，不覆盖用户自定义）
settings.security = settings.security || {}
settings.security.auth = settings.security.auth || {}
if (settings.security.auth.selectedType === undefined) {
  settings.security.auth.selectedType = 'gemini-api-key'
}

fs.writeFileSync(settingsPath, JSON.stringify(settings, null, 2))

// 2. 读取 .env 模板并与现有 .env 合并
const existingEnv = options.mode === 'overwrite' ? {} : loadEnvFile(envPath)
const existingGeminiModel = existingEnv.GEMINI_MODEL
const templateEnv = loadGeminiEnvTemplate(provider)
const env = { ...existingEnv, ...templateEnv }

// 常规 merge 时，模板默认模型不能覆盖用户已有模型
if (options.mode !== 'overwrite' && existingGeminiModel) {
  env.GEMINI_MODEL = existingGeminiModel
}

// 处理 provider.model（可能是 JSON 元数据或纯字符串）
if (provider.model) {
  try {
    const meta = JSON.parse(provider.model)
    // 合并 meta.env 到 .env
    if (meta.env) Object.assign(env, meta.env)
    // meta.env 是显式配置；defaultModel 只填空值，overwrite 时可覆盖模板默认
    if (meta.env) Object.assign(env, meta.env)
    if (meta.defaultModel && (!existingGeminiModel || options.mode === 'overwrite')) {
      env.GEMINI_MODEL = meta.defaultModel
    }
  } catch {
    // 不是 JSON，当作普通模型名称
    env.GEMINI_MODEL = provider.model
  }
}

saveEnvFile(envPath, env) // 按 KEY 排序写入
```

**保证**：

- ✅ settings.json/.env 支持模板化（统一与其他工具一致）
- ✅ 用户的其他 `settings.json` 配置不会丢失
- ✅ 用户的其他 `.env` 变量不会丢失
- ✅ 常规 merge 保留已有 `GEMINI_MODEL`；纯字符串 `provider.model` 或 `meta.env` 可显式覆盖
- ✅ `meta.defaultModel` 只在没有已有模型或 overwrite 时覆盖模板默认值
- ✅ 支持 JSON 元数据（高级用法）

### 6. Gemini CLI 如何读取配置

**启动时**：

1. 读取 `~/.gemini/settings.json`
2. 检查 `ide.enabled` 是否为 true
3. 读取 `~/.gemini/.env` 获取环境变量
4. 从 `GEMINI_API_KEY` 获取 API Key
5. 从 `GOOGLE_GEMINI_BASE_URL` 获取 Base URL
6. 从 `GEMINI_MODEL` 获取模型名称
7. 使用这些配置连接 API 服务

**环境变量优先级**：

```
系统环境变量 > ~/.gemini/.env > 默认值
```

## 五、OpenCode 配置原理

### 1. 配置文件路径

```
~/.config/opencode/opencode.json
```

### 2. 配置文件结构

```json
{
  "$schema": "https://opencode.ai/config.json",
  "model": "openai/gpt-5.5",
  "agent": {
    "build": { "options": { "store": false } },
    "plan": { "options": { "store": false } }
  },
  "provider": {
    "openai": {
      "options": {
        "baseURL": "https://okmcode.com",
        "apiKey": "sk-ant-xxx"
      },
      "models": {
        "gpt-5.5": {
          "name": "GPT-5.5",
          "options": { "store": false },
          "variants": { "low": {}, "medium": {}, "high": {}, "xhigh": {} }
        }
      }
    }
  }
}
```

### 3. 关键字段说明

| 字段                                     | 作用               | anyaitools 管理                     |
| ---------------------------------------- | ------------------ | ----------------------------------- |
| `$schema`                                | JSON Schema URL    | ✅ 固定值                           |
| `model`                                  | 默认模型           | ✅ 固定为 `openai/gpt-5.5`          |
| `provider.openai.options.baseURL`        | API 基础 URL       | ✅ 强制更新为 provider.baseUrl      |
| `provider.openai.options.apiKey`         | API 密钥           | ✅ 强制更新为 provider.apiKey       |
| `provider.openai.models`                 | 模型配置           | ✅ 管理 gpt-5.5，保留显式自定义模型 |
| `agent.build/plan.options.store`         | 响应存储开关       | ✅ 强制为 false                     |
| `provider.openai.models.*.options.store` | 模型级响应存储开关 | ✅ 托管模型强制为 false             |

### 4. 写入策略（零破坏性）

**代码位置**：`packages/core/src/writers/opencode.ts`

**流程**：

```typescript
// 1. 读取现有配置
const existingConfig = fileExists(configPath) ? readJSON(configPath) : {}

// 2. 从模板生成默认配置，并按模式合并现有配置
const meta = parseProviderMeta(provider.model)
const defaultConfig = replaceVariables(loadOpenCodeTemplateConfig(), {
  baseUrl: provider.baseUrl,
  apiKey: provider.apiKey,
})
const mergedConfig = deepMerge(defaultConfig, existingConfig)

// 3. 固定更新 provider.openai，并强制隐私相关 store=false
const existingProvider = mergedConfig.provider?.openai
const models = enforceModelStoreFalse(meta?.models || existingProvider?.models)
const managedProvider = {
  ...existingProvider,
  options: {
    ...(existingProvider?.options || {}),
    baseURL: provider.baseUrl,
    apiKey: provider.apiKey,
  },
  models,
}

// 4. 保留其他 provider，更新顶层模型和 agent 配置
const nextConfig = {
  ...mergedConfig,
  $schema: 'https://opencode.ai/config.json',
  model: 'openai/gpt-5.5',
  agent: enforceAgentStoreFalse(mergedConfig.agent),
  provider: {
    ...(mergedConfig.provider || {}),
    openai: managedProvider,
  },
}

// 5. 写入配置文件
writeJSON(configPath, nextConfig)
```

**保证**：

- ✅ 其他 provider 的配置不会丢失
- ✅ 常规 merge 保留 `provider.openai` 的其他 options 和用户自定义模型
- ✅ 自动移除旧托管模型键，但显式 `provider.model` JSON 元数据中的 models 会保留
- ✅ overwrite 仅写入当前托管结构

### 5. OpenCode 如何读取配置

**启动时**：

1. 读取 `~/.config/opencode/opencode.json`
2. 从顶层 `model` 读取默认的 `provider/model` 组合
3. 从 `provider.openai.options` 读取 Base URL 和 API Key
4. 从 `provider.openai.models` 获取可用模型和变体
5. 使用这些配置连接 API 服务

**配置优先级**：

```
opencode.json > 默认值
```

## 六、配置同步机制

### 1. 何时触发配置写入

**ToolManager 操作**：

```typescript
manager.switch(id) // ✅ 立即写入配置
manager.edit(id, updates) // ✅ 如果是当前激活的 provider，立即写入
manager.add(input) // ❌ 不写入（需要手动 switch）
manager.remove(id) // ❌ 不写入（只删除 provider 数据）
```

**特殊情况（MCP）**：

```typescript
// MCP 配置了 autoSync: true
manager.add(input) // ✅ 立即同步到 ~/.claude.json
manager.edit(id, updates) // ✅ 立即同步
manager.remove(id) // ✅ 立即同步
```

### 2. 配置文件关系

```
用户操作
  ↓
~/.anyaitools/{tool}.json (Provider 数据)
  ↓
ToolManager.switch()
  ↓
Writer 函数
  ↓
工具官方配置文件
  ↓
工具读取并生效
```

**数据流向**：

- **单向**：anyaitools → 工具配置文件
- **不回读**：工具配置文件的手动修改不会同步回 anyaitools

### 3. 配置冲突处理

**场景 1：用户手动修改了工具配置文件**

```
用户修改 ~/.claude/settings.json
  ↓
anyaitools switch 到另一个 provider
  ↓
Claude/Gemini/OpenCode/Codex：常规管理会保留非托管字段，并更新认证或当前 provider
  ↓
明确废弃字段会被清理；快捷配置入口才按模板覆盖
```

**场景 2：用户在工具中切换了服务商**

```
用户在 Codex 中手动修改 model_provider
  ↓
anyaitools 不会感知到这个变化
  ↓
anyaitools switch 会覆盖用户的修改
```

**建议**：

- ✅ 使用 anyaitools 统一管理服务商切换
- ❌ 不要在工具中手动修改服务商配置

## 七、高级用法：JSON 元数据

### 1. Gemini CLI 的 JSON 元数据

**场景**：需要设置多个环境变量

```typescript
// 添加 provider 时，model 字段使用 JSON
manager.add({
  name: 'Custom Gemini',
  baseUrl: 'https://api.example.com',
  apiKey: 'sk-xxx',
  model: JSON.stringify({
    defaultModel: 'gemini-3.5-flash',
    env: {
      GEMINI_MODEL: 'gemini-3.5-flash',
      GEMINI_TEMPERATURE: '0.7',
      GEMINI_MAX_TOKENS: '8192',
    },
  }),
})
```

**写入结果**（~/.gemini/.env）：

```bash
GEMINI_API_KEY=sk-xxx
GEMINI_MAX_TOKENS=8192
GEMINI_MODEL=gemini-3.5-flash
GEMINI_TEMPERATURE=0.7
GOOGLE_GEMINI_BASE_URL=https://api.example.com
```

```json

      "name": "Custom OpenAI",
      "options": {
        "baseURL": "https://api.example.com",
        "apiKey": "sk-xxx"

        "custom-model": {

              "reasoningEffort": "high",
              "textVerbosity": "low",
              "reasoningSummary": "auto"
            }
          }
```

## 八、故障排查

### 1. 配置未生效

**症状**：执行 `anyaitools switch` 后，工具仍然使用旧配置

**排查步骤**：

```bash
# 1. 确认 anyaitools 配置正确
anyaitools {tool} current

# 2. 检查工具配置文件是否更新
cat ~/.claude/settings.json  # Claude
cat ~/.codex/config.toml     # Codex
cat ~/.gemini/.env           # Gemini
cat ~/.config/opencode/opencode.json  # OpenCode

# 3. 重启工具
# 大多数工具需要重启才能读取新配置
```

**常见原因**：

- ❌ 工具未重启
- ❌ 工具使用了缓存的配置
- ❌ 工具从其他位置读取配置（环境变量优先级更高）

### 2. 配置被覆盖

**症状**：用户的自定义配置丢失

**排查步骤**：

```bash
# 1. 检查是否是认证字段
# 认证字段（apiKey, baseUrl）会被强制覆盖，这是预期行为

# 2. 如果是 Codex 常规切换
# 非托管字段应保留；当前 provider 的认证来源字段会被规范化

# 3. 如果使用了 aat okm / aicoding / standalone 等快捷入口
# 快捷入口会覆盖其托管配置，请检查入口创建的备份

# 4. 查看备份文件（如果有）
ls -la ~/.claude/settings.json.bak
```

**解决方案**：

- ✅ 认证字段：使用 anyaitools 管理，不要手动修改
- ✅ Codex 常规切换：合法自定义字段丢失属于 bug；损坏配置会中止而不是覆盖
- ✅ 快捷覆盖：从该入口创建的 `.bak` 或事务备份恢复
- ✅ 其他工具：其他字段应该被保留，如果丢失请报告 bug

### 3. TOML 注释丢失（Codex）

**症状**：`~/.codex/config.toml` 中的注释消失

**原因**：TOML 解析器的已知限制

**解决方案**：

- ✅ 将注释放在单独文档中；结构化配置字段在常规 merge 中仍会保留

## 九、总结

### 1. 核心原则

**安全写入**：

- ✅ 常规 provider 管理增量更新，解析失败时 fail closed
- ✅ 快捷覆盖和其他高风险入口在写入前创建备份
- ✅ 认证字段始终按当前服务商写入
- ✅ Codex 会清理明确废弃键，同时保留有效用户配置

**统一管理**：

- ✅ 所有工具共用同一套 Provider 数据模型
- ✅ 统一的 CRUD 操作接口
- ✅ 统一的配置写入流程

**简洁实现**：

- ✅ 每个 Writer 只做一件事：写入配置
- ✅ 没有复杂的抽象层
- ✅ 直接硬编码 4 个 Writer 函数
