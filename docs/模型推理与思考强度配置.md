# 模型推理与思考强度配置

本文记录当前项目支持的各类工具如何设置模型推理、思考或 effort。它是实现
“按工具选择模型和推理强度”功能的依据。

> 查询基准：2026-07-27。官方 CLI、模型目录和 provider 能力会变化，以下内容描述
> 配置语义和字段映射，不把某一次目录返回的模型 ID 当成永久不变的值。

## 先看结论

| 工具        | 模型字段                                    | 强度/思考字段                                                  | 是否能统一成 `low/high`                    |
| ----------- | ------------------------------------------- | -------------------------------------------------------------- | ------------------------------------------ |
| Codex       | `model`                                     | `model_reasoning_effort`、`plan_mode_reasoning_effort`         | 只能作为显示层快捷值，落盘必须保留官方枚举 |
| Claude Code | `model`                                     | `effortLevel`、`CLAUDE_CODE_EFFORT_LEVEL`                      | 只能按模型能力动态显示                     |
| Gemini CLI  | `model.name`                                | `thinkingConfig.thinkingBudget`、`includeThoughts`             | 不能，预算是数字且模型相关                 |
| OpenCode    | `provider/model-id`                         | `variants` 中的 `reasoningEffort` 等选项                       | 不能，variant 是配置档位                   |
| OpenClaw    | `provider/model-id`                         | `thinkingDefault`、模型 profile 的 `supportedReasoningEfforts` | 只能按 profile 返回值显示                  |
| Grok Build  | `[models].default`、`[model.<alias>].model` | `default_reasoning_effort`、`reasoning_effort`                 | 只能在 endpoint 声明支持时显示             |

MCP 不在这张表中。MCP 是宿主工具的外部 server 配置，不拥有模型 ID、模型目录、
推理强度或思考可见性。

## 先区分三个概念

### 1. 模型选择

决定使用哪个模型，例如 `openai/gpt-5.5`、`anthropic/claude-opus-5`。

### 2. 推理强度

决定模型愿意花多少 token 或时间进行推理。常见名称有 `low`、`medium`、`high`、
`xhigh`，但每个工具和模型支持的值可能不同。

### 3. 思考可见性

决定是否显示或保留 reasoning/thinking 内容。它和推理强度不是一回事：

- 推理强度高，不代表一定显示思考内容。
- 关闭思考可见性，不一定等于模型完全停止内部推理。
- 某些模型只支持二元开关，某些模型支持完整 effort 档位。

因此 AnyAI Tools 不应把所有工具统一成一个 `reasoningEffort` 字符串，而应按
工具保存结构化模型元数据，并记录能力来源和可用值。

## Codex

### 模型

Codex 支持：

- 交互式 `/model`
- 启动参数 `codex --model <id>`
- `~/.codex/config.toml` 的根级 `model`
- 新线程默认值 `[models.new_thread].model`

### 推理强度

主要配置：

```toml
model_reasoning_effort = "high"
plan_mode_reasoning_effort = "high"
model_reasoning_summary = "auto"
model_verbosity = "high"
```

当前官方支持的通用 effort 值为：

```text
none | minimal | low | medium | high | xhigh
```

`none` 表示不主动传递 reasoning effort；`xhigh` 是模型相关能力，不应对所有模型
强行展示。交互式 `/model` 可能显示模型或客户端特有选项，AnyAI Tools 应以实际
模型能力返回为准，而不是把这些值写死为所有 Codex 模型通用。

`plan_mode_reasoning_effort` 与普通运行的 effort 独立；`model_reasoning_summary`
只控制摘要策略；`model_verbosity` 只控制输出详略，三者都不应伪装成模型 ID。

### 实现注意

- `model_reasoning_effort` 与 `plan_mode_reasoning_effort` 是两个独立字段。
- `review_model` 只决定 `/review` 使用的模型，不是推理强度。
- `model_reasoning_summary` 控制摘要详情，不等于思考预算。
- 自定义 provider 通常没有官方模型目录，不能保证能自动拉取模型或 effort。

官方资料：

- <https://developers.openai.com/codex/config-reference>
- <https://developers.openai.com/codex/models>
- <https://developers.openai.com/codex/developer-commands>

## Claude Code

### 模型

模型可以通过以下入口选择：

- `settings.json` 的 `model`
- `claude --model <id>`
- 会话内 `/model`

### Effort

持久设置：

```json
{
  "effortLevel": "high"
}
```

临时设置：

```bash
claude --effort high
```

会话内设置：

```text
/effort
/effort high
/effort auto
```

常见官方 effort 级别包括：

```text
low | medium | high | xhigh | max
```

可用档位按模型、账户和组织策略变化。`max` 与 `ultracode` 不能简单当成所有模型
都可持久化的 effort 值；`ultracode` 也不是模型 effort，而是 Claude Code 的
额外工作流设置。UI 必须把它们作为能力元数据或会话级选项处理。

环境变量：

```bash
CLAUDE_CODE_EFFORT_LEVEL=high
```

它的优先级高于 `/effort` 和 `effortLevel`。思考显示和 effort 还要分开处理：

- `alwaysThinkingEnabled`：默认启用 extended thinking。
- `MAX_THINKING_TOKENS=0`：在支持的模型上关闭思考参数。
- `Ctrl+O`：切换思考内容的详细显示。

### 实现注意

- AnyAI Tools 不能只保存一个固定的 `reasoningEffort`，要保存 `effortLevel`，
  并记录 `max`/`ultracode` 是否仅会话有效。
- `/model` 选择器本身还可能带 effort 滑块。
- 第三方 provider 可能不支持 Anthropic 原生 thinking 参数。

官方资料：

- <https://code.claude.com/docs/en/model-config>
- <https://code.claude.com/docs/en/settings>
- <https://code.claude.com/docs/en/env-vars>
- <https://code.claude.com/docs/en/commands>

## Gemini CLI

### 模型

模型选择入口：

- `/model`
- `gemini --model <id>`
- `gemini -m <id>`
- `settings.json` 的模型配置

Gemini CLI 的 `/model` 支持 Auto、Pro、Flash 和手动指定具体模型；子 agent 的模型
可能独立于主会话模型。

### 思考配置

高级模型配置位于 `settings.json` 的 `modelConfigs`。通用结构如下：

```json
{
  "modelConfigs": {
    "customAliases": {
      "deep-reasoning": {
        "modelConfig": {
          "model": "gemini-model-id",
          "generateContentConfig": {
            "thinkingConfig": {
              "thinkingBudget": 4096,
              "includeThoughts": true
            }
          }
        }
      }
    }
  }
}
```

`thinkingBudget` 是模型相关的预算值，不是跨模型通用的 `low/high` 枚举。
Gemini CLI 还支持通过 `modelConfigs.overrides` 按模型或 agent scope 注入配置；
常见的 `temperature`、`topP`、`maxOutputTokens` 也属于同一套
`generateContentConfig`。

预算的最小值、最大值、是否允许 `-1`/自动值由具体模型和 provider 决定。目录未
返回预算范围时，AnyAI Tools 只能提供数字输入和“未设置”，不能替用户猜一个
跨模型通用的预算。

### 实现注意

- 模型列表可以来自 Gemini CLI 自身的 `/model` 目录和服务商访问权限。
- 通过第三方 Base URL 时，官方 Gemini 模型目录不一定适用。
- AnyAI Tools 同时写入官方 `model.name`、兼容的 `GEMINI_MODEL` 和可选的
  `modelConfigs`，避免新旧 Gemini CLI 版本读取结果不一致。
- UI 不能把 `thinkingBudget` 伪装成固定的 `low/medium/high`，应根据模型能力
  显示数字输入或关闭/自动选项。

官方资料：

- <https://geminicli.com/docs/cli/model/>
- <https://geminicli.com/docs/cli/generation-settings/>
- <https://geminicli.com/docs/reference/configuration/>

## OpenCode

### 模型

模型格式为：

```text
provider/model-id
```

模型目录主要来自 Models.dev，也可以来自本地 provider 配置：

```bash
opencode models
opencode --model provider/model-id
opencode -m provider/model-id
```

### 推理强度

OpenCode 用 variant 表示同一个模型的不同运行档位：

```json
{
  "provider": {
    "openai": {
      "models": {
        "gpt-5.5": {
          "variants": {
            "low": {
              "reasoningEffort": "low"
            },
            "high": {
              "reasoningEffort": "high",
              "textVerbosity": "low",
              "reasoningSummary": "auto"
            }
          }
        }
      }
    }
  }
}
```

variant 内既可以保存 `reasoningEffort`，也可以保存 `textVerbosity`、
`reasoningSummary`、`temperature` 等 provider 选项。模型级 `options` 与 variant
是两个层级：前者是所有 variant 共用的参数，后者只在选择该档位时生效。

官方内置 variant 会按 provider 和模型变化：

- Anthropic 常见 `high`、`max`
- OpenAI 常见 `none`、`minimal`、`low`、`medium`、`high`、`xhigh`
- Google 常见 `low`、`high`

variant 是配置档位，不是新的模型 ID。`variant_cycle` 可以在会话中快速切换。

### 实现注意

- 自动拉取列表应使用 Models.dev/OpenCode provider 数据，同时保留手动输入入口。
- 对自定义 provider，必须允许用户自定义模型 ID 和 variant。
- AnyAI Tools 读取 `modelConfig.modelId` 并维护所选模型的 variants；没有结构化模型
  配置时才回退到旧的 `openai/gpt-5.5` 模板。

官方资料：

- <https://opencode.ai/docs/models/>
- <https://opencode.ai/docs/config/>
- <https://opencode.ai/docs/cli/>

## OpenClaw

### 模型

模型引用格式为：

```text
provider/model-id
```

官方 CLI：

```bash
openclaw models list
openclaw models status
openclaw models set provider/model-id
openclaw models set-image provider/model-id
```

OpenClaw 的官方 provider plugin 会提供模型目录、认证和模型能力。自定义 provider
则由 `models.providers.<provider>.models[]` 声明。

### 思考强度

OpenClaw 使用 `/think` 和 `thinkingDefault`。可用值由当前 provider/model profile
决定，常见值包括：

```text
off | minimal | low | medium | high | xhigh | adaptive | max
```

配置示例：

```json5
{
  agents: {
    defaults: {
      thinkingDefault: 'high',
      models: {
        'provider/model-id': {
          compat: {
            supportedReasoningEfforts: ['low', 'medium', 'high'],
          },
        },
      },
    },
  },
}
```

OpenAI、Anthropic、Gemini、Qwen、Z.AI 等 provider 对 thinking 的映射可能不同：

- 有些 provider 支持完整 effort 梯度。
- 有些只支持 `off/on`。
- 有些把 `xhigh` 映射到 provider 自己的 `max`。
- 有些模型关闭 thinking 时不能传 `reasoning.effort: "none"`。

因此 OpenClaw 的 UI/CLI 会根据模型 profile 动态限制 `/think` 选项。

### 实现注意

- 自动拉取模型时优先使用 `openclaw models list --json` 或官方 provider catalog。
- AnyAI Tools 自定义 endpoint 必须允许配置 `supportedReasoningEfforts` 和映射规则。
- `reasoningDefault` 是思考内容可见性，不是 effort：
  `off | on | stream`。
- `imageModel`、fallback 和 utility model 也可能各自有模型配置，不能只保存一个
  全局 reasoning 值。

官方资料：

- <https://docs.openclaw.ai/concepts/model-providers>
- <https://docs.openclaw.ai/tools/thinking>
- <https://docs.openclaw.ai/gateway/config-agents>
- <https://docs.openclaw.ai/cli/models>

## xAI Grok Build

### 模型

Grok Build 支持：

- `[models].default`
- `[model.<alias>]`
- `-m` / `--model`
- `GROK_DEFAULT_MODEL`
- 自定义模型目录 URL：`GROK_MODELS_BASE_URL`、`GROK_MODELS_LIST_URL`

### 推理强度

用户级配置：

```toml
[models]
default = "custom"
default_reasoning_effort = "high"

[model.custom]
model = "model-id"
supports_reasoning_effort = true
reasoning_effort = "high"
```

官方设置还区分：

- `GROK_SHOW_THINKING_BLOCKS=1`：在 TUI 显示 reasoning/thinking blocks。
- `default_reasoning_effort`：默认模型的推理强度。
- `reasoning_effort`：指定自定义模型的推理强度。
- `supports_reasoning_effort`：是否声明该 endpoint 支持推理控制。

显示思考块和提高推理强度是两件事，不能合并成一个 UI 开关。

### 实现注意

- Grok Build 是当前项目中最适合直接实现模型目录拉取的工具之一，因为官方支持
  `GROK_MODELS_LIST_URL`。
- 拉取失败时应保留手动输入和上次缓存，不能清空用户模型。
- 自定义 endpoint 的 effort 值由 endpoint 决定，不能默认套用 xAI 官方模型的值。

Grok Build 的 `GROK_SHOW_THINKING_BLOCKS` 只控制 TUI 是否显示 thinking blocks，
与 `reasoning_effort` 相互独立。AnyAI Tools 应在 UI 中分开显示这两个开关。

官方资料：

- <https://docs.x.ai/build/settings>
- <https://docs.x.ai/build/settings/reference>

## MCP

MCP 不属于 Codex、Claude Code、Gemini CLI、OpenCode、OpenClaw、Grok Build 这一层级
的模型工具。它只是宿主工具的外部工具协议配置。

MCP 没有模型列表、模型 ID、推理强度或思考模式。MCP server 可以被多个宿主工具
使用，但模型和 reasoning 始终由宿主工具单独决定。

## 对 AnyAI Tools 的统一设计结论

### 统一模型配置到官方字段的映射

| AnyAI Tools 字段       | Codex                         | Claude Code                      | Gemini CLI                         | OpenCode                           | OpenClaw                           | Grok Build                            |
| ---------------------- | ----------------------------- | -------------------------------- | ---------------------------------- | ---------------------------------- | ---------------------------------- | ------------------------------------- |
| `modelConfig.modelId`  | `model`                       | `settings.model`                 | `model.name` 与兼容 `GEMINI_MODEL` | 顶层 `model`，必须含 provider 前缀 | `agents.defaults.model.primary`    | `[model.<alias>].model` 或 catalog ID |
| `modelConfig.variant`  | 不使用                        | 不使用                           | 不使用                             | 选择 `models.<id>.variants.<name>` | 不使用                             | 不使用                                |
| `reasoning.mode/value` | `model_reasoning_effort`      | `effortLevel`                    | `thinkingBudget`                   | variant/options                    | `thinkingDefault`                  | `reasoning_effort`                    |
| `reasoning.visible`    | 摘要策略之外不控制显示        | `alwaysThinkingEnabled`/环境变量 | `includeThoughts`                  | 由 variant/options 决定            | `reasoningDefault` 或会话 `/think` | `GROK_SHOW_THINKING_BLOCKS`           |
| `parameters`           | plan/review/summary/verbosity | thinking token、effort 兼容参数  | `generateContentConfig`            | provider options                   | fallback、image model、profile     | backend 与 endpoint 能力              |

### 目录失败时的行为

模型目录的自动拉取不是配置正确性的前提。每个模型工具都必须保留以下后备链：

1. 用户手动输入的模型 ID；
2. AnyAI Tools 的本地模型 metadata 缓存；
3. 当前 Provider 已保存的模型和推理配置；
4. 没有模型时才使用模板默认值。

缓存只保存模型 ID、显示名、能力、variants 和可用强度，不保存 API Key。

### 不建议的设计

不要在通用 Provider 上只增加：

```typescript
model?: string
reasoningEffort?: string
```

这会丢失 OpenCode variant、Gemini thinking budget、OpenClaw provider profile、
Grok model endpoint 等信息。

### 建议的结构

```typescript
interface ToolModelConfig {
  modelId?: string
  displayName?: string
  source: 'catalog' | 'manual' | 'cached'
  catalogProvider?: string
  variants?: Record<string, Record<string, unknown>>
  reasoning?: {
    mode: 'effort' | 'thinking' | 'budget' | 'variant' | 'unsupported'
    value?: string | number
    supportedValues?: Array<string | number>
    visible?: boolean
  }
  raw?: Record<string, unknown>
}
```

每个工具的 writer 再把这个结构映射到自己的官方配置格式。MCP 不进入这个模型
配置结构，只通过独立的 MCP 管理器同步到宿主工具。
